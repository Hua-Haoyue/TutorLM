# Control-plane CLI

`control_plane` is the runtime-host control plane. Its CLI both serves the
control plane and administers a running instance over HTTP.

## Where to run it

Run from `runtime-host/control-plane`, or from any directory where that
directory is importable (for example a repository-root invocation with
`PYTHONPATH` set):

```powershell
$env:PYTHONPATH = "$PWD\runtime-host\control-plane"
python -m control_plane --help
```

## Serving

The legacy startup form is preserved exactly:

```text
python -m control_plane --host 127.0.0.1 --port 8090 --log-level info --no-startup-tasks
```

`serve` is the explicit equivalent and additionally accepts `--config`:

```text
python -m control_plane serve --config runtime-host/deploy/control-plane.toml
```

`serve` and the bare form both accept `--host`, `--port`, `--log-level`,
`--no-startup-tasks` and `--config`.

## Configuration

Configuration files are **TOML only** and are read with the standard library
`tomllib`. The CLI does not implement its own config parser, does not support
ad-hoc JSON or dotenv files, and never mutates the process environment. It
delegates entirely to the worker entry point:

```python
ControlPlaneConfig.from_env(environ, config_path="path/to/control-plane.toml")
```

The path comes from `--config`, or from the `CONTROL_PLANE_CONFIG` environment
variable when `--config` is absent. `--config` wins over the environment. Shell
environment values keep their normal precedence over file values inside the
worker. The CLI never reads the file itself, so an unreadable or malformed
path surfaces as the worker's own configuration error.

## Management over HTTP

Management commands are HTTP clients of a running control plane. They never
open the database or import server internals.

Global options (accepted before or after the subcommand):

* `--url URL` — control-plane base URL, default `http://127.0.0.1:8090`.
* `--config PATH` — TOML configuration file (see above).

Credentials travel only in headers, never in the URL and never in logs.
The admin token is read from `ControlPlaneConfig.admin_token`
(`CONTROL_PLANE_ADMIN_TOKEN`) and sent as `X-Admin-Token`. Sharing commands
read the user identity from `TUTORLM_USER_ID` / `TUTORLM_USER_TOKEN` and send
them as `X-User-ID` / `X-User-Token`.

### Commands

```text
status
slots list
slots reclaim SLOT_ID
slots drain SLOT_ID
slots release-quarantine SLOT_ID
leases [--limit N]
events [--limit N]
reconcile
gc
config
invitations list
invitations create [--label LABEL]
invitations delete INVITATION_ID
shares create WORKSPACE_ID [--label LABEL]
shares revoke WORKSPACE_ID INVITATION_ID
shares import CODE [--title TITLE]
user register
user login --user-id USER_ID --recovery-token TOKEN
```

### Endpoint mapping

| Command | HTTP |
| --- | --- |
| `status` | `GET /control/health` + `GET /control/capacity` |
| `slots list` | `GET /control/admin/slots` |
| `slots reclaim\|drain\|release-quarantine ID` | `POST /control/admin/slots/{id}/{action}` |
| `leases` | `GET /control/admin/leases?limit=N` |
| `events` | `GET /control/admin/events?limit=N` |
| `reconcile` | `POST /control/admin/reconcile` |
| `gc` | `POST /control/admin/gc` |
| `config` | `GET /control/admin/config` (server-redacted summary) |
| `invitations list` | `GET /control/admin/invitations` |
| `invitations create [--label]` | `POST /control/admin/invitations` JSON `{label}` |
| `invitations delete ID` | `DELETE /control/admin/invitations/{id}` |
| `shares create WORKSPACE_ID [--label]` | `POST /control/workspaces/{id}/invitations` JSON `{}` or `{label}` |
| `shares revoke WORKSPACE_ID ID` | `DELETE /control/workspaces/{id}/invitations/{id}` |
| `shares import CODE [--title]` | `POST /control/workspace-imports` JSON `{invitation_code, title?}` |
| `user register` | `POST /control/users` |
| `user login` | `POST /control/users/session` JSON `{user_id, recovery_token}` |

### Output and responses

Any `2xx` is success: `200`, `201`, `202` and `204` are all accepted and the
JSON body is printed to stdout as-is. The CLI does **not** hardcode response
shapes, so an endpoint may return `200`/`201` synchronously or `202` with a
`workspace` object and both work. A body-less success (e.g. `204`) prints
`{"status": "ok"}`. Recovery codes and invitation codes generated by the
server are printed once to stdout so the user can act on them immediately;
they are never written to any log and never appear in error output.

## Exit codes

* `0` — server started, or an HTTP command received a `2xx` response.
* `1` — invalid local configuration, transport failure, or a non-`2xx` HTTP
  response. The message goes to stderr and never includes the original request
  credentials or the submitted code/token.
* `2` — argparse usage error (missing or invalid arguments).

All commands use the same configuration failure handling: invalid TOML,
validation failures (including duplicate system invitation codes), and expected
file access/encoding failures print a fixed configuration error to stderr and
return `1`. Raw exception messages and tracebacks are not printed because they
may contain credentials or config source lines. Programming errors such as
`TypeError` are not converted into configuration failures.
